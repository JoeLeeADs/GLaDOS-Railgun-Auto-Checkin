# GLaDOS / Railgun 自动签到（合体版）

基于 [Devilstore/Glados-Railgun-checkin](https://github.com/Devilstore/Glados-Railgun-checkin) 与
[MZRidaz/GLaDOS-Auto-Checkin](https://github.com/MZRidaz/GLaDOS-Auto-Checkin) 整合的自动签到脚本，
运行在 GitHub Actions 上，无需服务器、无需编程基础。

## ✨ 功能特性

- 🌐 **多服务自适应**：内置 GLaDOS / Railgun 等多个候选域名，**首次探测到可用域名即锁定复用**，应对官方反复改域名
- 📱 **设备平台自适应重试**：遇到 `code 4 device-mismatch` 自动按 `loginDevice` 切换 UA 重试，无需手动配 UA
- 📬 **8 路推送**：PushDeer / Server酱 / Telegram / PushPlus / 钉钉 / 飞书 / 企业微信 / 云湖
- 🔒 **Cookie 前缀无关校验 + 归一化**：`koa:` / `gld:` / 任意前缀自动兼容，自动去引号与 `Cookie:` 头名
- 🛡️ **隐私脱敏**：日志中邮箱 / Cookie 自动打码
- 💎 **积分兑换阈值保护**：总积分达标才兑换，不浪费积分（可选）
- 🎯 **兑换邮箱白名单**：`EXCHANGE_EMAILS` 可只兑指定账号；名单外账号完全不发起兑换请求
- ♻️ **签到失败自动重试**：网络错误 / HTTP 错误 / 未知业务失败各**自动重试一次**；鉴权失败重试无意义，直接跳过
- ⏰ **定时兜底**：一天两次（主运行 09:18 + 兜底 21:18），**当天已签到则静默跳过推送**，既防漏签又不重复刷屏
- 🔄 **网络重试 + 退出码区分**：全部失败标红（退出码 1），区分「业务失败」与「通知失败」
- 🔗 **LifeLoom 双写上报**：原有 8 路通知完全不变，另把本轮**全量结构化结果** POST 给 LifeLoom 签到聚合页；上报失败绝不影响签到
- 👥 **多账号**：`COOKIES` 支持 `|||` / `&` / 换行 三种分隔

## 🚀 使用教程

### 1. Fork 本项目到你的 GitHub

右上角 **Fork** → 到你自己的仓库。

### 2. 获取站点 Cookie

1. 浏览器登录 [https://glados.cloud](https://glados.cloud)（或 Railgun 站点）
2. 按 **F12** → **Application**（或 **Storage**）→ **Cookies** → 复制完整 Cookie 值

示例（现网签发 `gld:` 前缀，旧版 `koa:` 同样支持）：

```
gld:sess=xxxxxx; gld:sess.sig=yyyyyy
```

> ⚠️ `sess` 与 `sess.sig` 必须同时存在、前缀一致。脚本会自动识别任意前缀。

### 3. 配置 GitHub Secrets

仓库 **Settings → Secrets and variables → Actions → Secrets → New repository secret**：

| Secret 名 | 说明 | 必填 |
| --- | --- | --- |
| `COOKIES` 或 `GLADOS_COOKIES` | Cookie 值；多账号用 `\|\|\|` / `&` / 换行分隔 | ✅ |
| `DOMAINS` | 候选域名（逗号分隔），覆盖默认值，如 `glados.cloud,railgun.info` | ❌ |
| `EXCHANGE_PLAN` 或 `GLADOS_EXCHANGE_PLAN` | 兑换计划：`plan100` / `plan200` / `plan500`，不配则不兑换 | ❌ |
| `EXCHANGE_EMAILS` | 兑换邮箱白名单（逗号分隔），只兑名单内账号；不配则不限制。也可放 Variables | ❌ |
| `SENDKEY` | PushDeer 推送 key | ❌ |
| `SERVERCHAN_KEY` | Server酱 key | ❌ |
| `TG_BOT_TOKEN` + `TG_CHAT_ID` | Telegram 机器人 | ❌ |
| `PUSHPLUS_TOKEN` | PushPlus token | ❌ |
| `DINGTALK_WEBHOOK` (+ `DINGTALK_SECRET`) | 钉钉机器人（加签需配 secret） | ❌ |
| `FEISHU_WEBHOOK` (+ `FEISHU_SECRET`) | 飞书机器人（加签需配 secret） | ❌ |
| `WECOM_BOT_WEBHOOK` | 企业微信机器人 | ❌ |
| `YUNHU_TOKEN` + `YUNHU_RECV_ID` (+ `YUNHU_RECV_TYPE`) | 云湖机器人 | ❌ |
| `LIFELOOM_HOOK_URL` | LifeLoom 上报地址（**含 token，务必放 Secret**）；不配则不上报 | ❌ |

> 推送渠道配哪个用哪个，可同时配多个。

### 4. 开启 Actions

**Actions** 标签页 → 启用工作流。定时任务**北京时间每天触发 2 次**：

| 时段（北京） | 作用 |
| --- | --- |
| **09:18** | 主运行（真正的签到在这时完成并推送通知） |
| **21:18** | 兜底：若 09:18 被 GitHub 漏跑/延迟，或当天签到失败，这次补上 |

**兜底不会造成重复通知**：脚本每次都会记录当天是否已签到 —— 只要当天该账号已签到，后续运行会**静默跳过推送**（日志里会写明「本轮无新签到事件，按策略跳过推送」）。所以正常情况下你**每天只会收到一条**带积分的通知。

也可在 Actions 页面手动 **Run workflow** 立即测试 —— 会有一个 **「本次是否推送通知」** 选项：

- **`always`（默认）**：本次一定推送，方便预览通知效果、排查问题
- **`auto`**：按脚本策略（当天已签到则静默跳过），用于只想验证签到是否正常、不想被通知打扰时

> 想改时间：编辑 `.github/workflows/checkin.yml` 里的 `cron`（分 时 日 月 周），`timezone` 保持 `Asia/Shanghai` 即可按北京时间解读。只想留一个时段，删掉多余的 `- cron` 条目即可。

## 💡 积分兑换说明

积分可以兑换成会员天数，但它**绝不会自动花你的积分** —— 必须显式指定兑换计划才会执行。

| 计划 | 消耗积分 | 兑换天数 | 折合成本 |
| --- | --- | --- | --- |
| `plan100` | 100 | 10 天 | 10 分/天 |
| `plan200` | 200 | 30 天 | ≈6.7 分/天 |
| `plan500` | 500 | 100 天 | 5 分/天 |

> 兑得越多越划算。无论用哪种方式，执行前都会先查总积分，**不够会自动跳过**并标记 `⏭️ 积分不足(x/所需)`，不会让你白花。

### 方式一：手动兑换一次（推荐）

某个号快到期、想单独给它换 30 天，又不想影响每日定时任务 —— 用这个方式。

#### 第 1 步：确认积分够不够

每天签到通知里会列出每个号的总积分（`总计 XXX 积分`）。也可以先去 **Actions → Run workflow** 把「本次兑换计划」选 `none` 跑一次 —— **只读不兑**，日志里就能看到实时余额。

#### 第 2 步：发起兑换

1. 打开仓库首页，点顶部 **Actions**
2. 左侧列表点 **GLaDOS/Railgun 自动签到**
3. 右上角点 **Run workflow**（下拉展开）
4. 按下表填字段：

| 字段 | 填什么 | 说明 |
| --- | --- | --- |
| **Use workflow from** | `Branch: main` | 默认值，不用改 |
| **本次是否推送通知** | `always` | 兑换后想在手机上看到结果就选它 |
| **本次兑换计划** | `plan200` | 200 分 → 30 天。换 10 天用 `plan100`，换 100 天用 `plan500`，不想兑用 `none` |
| **本次只对这些邮箱兑换** | 你的完整邮箱 | 只兑这一个号。**留空会兑所有账号**，多号用户务必填 |

5. 点绿色 **Run workflow** 按钮
6. 等 10~30 秒刷新页面，列表顶部会出现一条新的运行记录

#### 第 3 步：确认兑换结果

点进那条运行记录 → 左侧 **checkin** → 展开 **Run checkin**，重点看这几行：

```
兑换白名单已启用：liyiqiaoad@icloud.com（名单外账号一律不兑换）
账号 1(97***5@qq.com) 不在兑换白名单内，跳过兑换
账号 4 兑换成功：0 天 → 30 天（消耗 200 积分）
```

手机通知里则是：

```
4. li***d@icloud.com
   🔄 已签到 · 今日已领 · 剩余 30 天 · 总计 67 积分
   🌐 railgun.info · 🎁 兑换成功(+30天/-200分) 剩余 0 天→30 天
```

只要看到 `剩余 0 天→30 天`，就说明天数**真的到账了** —— 脚本兑换后会重新调一次接口核对天数和余额，不是只信那句"兑换成功"。

#### 第 4 步：兑换失败怎么查

| 日志/通知显示 | 含义 | 怎么处理 |
| --- | --- | --- |
| `⏭️ 积分不足(171/200)` | 积分不够这个计划 | 换 `plan100`，或继续签到攒分 |
| `⚠️ 兑换失败(...)` | 接口拒绝了 | 括号里是站点原话，按提示处理（多为积分不足或计划下架） |
| `⚠️ 兑换异常(...)` | 网络超时/断开 | 隔几分钟再发一次（**不要连点**，避免重复扣分） |
| `❌ 鉴权失败` | Cookie 已失效 | 重新获取 Cookie 更新 `COOKIES` Secret |
| 提示成功但天数没变 | 接口/页面缓存 | 过几分钟再跑一次只读（`none`）核对 |

> 💡 真实案例：2026-11-02 用这套流程给 `liyiqiaoad@icloud.com` 兑了 30 天 —— 兑换前 `0 天 / 267 分`，兑换后 `30 天 / 67 分`；同仓库另外 3 个账号日志显示「不在兑换白名单内，跳过兑换」，积分分文未动。

---

### 方式二：永久开启自动兑换

想让它**每天自动**把攒下的积分换成天数（攒够就兑，不够自动跳过），在 **Settings → Secrets and variables → Actions → Secrets** 里加：

| Secret 名 | 值 | 效果 |
| --- | --- | --- |
| `EXCHANGE_PLAN` | `plan200` | 每天签到后，哪个号够 200 分就自动兑 30 天 |

> 这是**长期生效**的配置。加进去后，每个号只要积分达标都会被兑 —— 只想兑某一个号，务必配合下面的白名单使用。

### 限定哪些账号可兑（邮箱白名单）

`EXCHANGE_EMAILS` 用来限定兑换范围，长期配置和临时兑换都支持：

```bash
EXCHANGE_EMAILS=liyiqiaoad@icloud.com          # 只兑这一个
EXCHANGE_EMAILS=a@x.com,b@y.com                # 兑这两个
# 不配置 = 不限制（对所有账号生效）
```

可以放 **Secrets**（长期、敏感），也可以放 **Variables**（长期、非敏感、可随时改）；手动触发时直接在 `Run workflow` 里填，则只对那一次生效。

安全设计：

- 匹配的是接口返回的**完整邮箱**，通知与日志里仍只显示脱敏值（`li***d@icloud.com`）；
- 若状态查询失败拿不到邮箱，该账号**一律不兑换**（宁可不兑，也不误兑别人）；
- 名单外账号**连兑换请求都不会发出**，日志记「不在兑换白名单内，跳过兑换」。

> ⚠️ 兑换是**消耗积分、不可逆**的操作。脚本**故意不做自动重试** —— 这类非幂等请求若重试，可能在"服务端已成功但响应丢失"时重复扣分。失败只如实报告，绝不自动再试。

## 🔗 LifeLoom 上报（双写）

原有 8 路通知**完全不动**，在同一轮的末尾额外把结果 POST 一份给 LifeLoom（家庭签到聚合页）。**双写、互不影响**：通知照旧发，LifeLoom 挂了只记一行日志。

### 接口约定

| 项目 | 值 |
| --- | --- |
| 地址 | 环境变量 `LIFELOOM_HOOK_URL`（值里已含 token，**不写死在代码里**） |
| 方法 / 头 | `POST` + `Content-Type: application/json` |
| 请求体 | ≤ 32KB（脚本序列化后自动核对字节数，超了会先瘦身，见下） |
| 频率 | 30 条/分钟；正常每天 1 条，远低于限制 |
| 成功判定 | **HTTP 201** 才算收下（NestJS 没有 200） |
| 413 | 请求体太大 → **不重试**，直接放弃并报错 |
| 429 | 发太快 → 等 `Retry-After`（没给就等 30 秒）后重试 |
| 其他 4xx | 参数/权限问题，重试无意义 → **不重试** |
| 5xx / 网络异常 | 重试，**最多 2 次、每次间隔 ≥30 秒**（总尝试 3 次）后放弃 |

> 安全网：整段逻辑（组装 + 序列化 + 发送 + 重试）都在 `try/except` 内，任何异常只记 `WARNING`，**不会改变签到结果与退出码**。

### 什么时候推

与通知**同频**，避免同一天重复灌同一条数据：

| 场景 | 通知 | LifeLoom |
| --- | --- | --- |
| 定时 09:18 正常签到（有成功或失败） | 推 | **推**（每天那条正常数据） |
| 定时 21:18 兜底，当天已全部签过 | 静默跳过 | 同步跳过（当天已有数据） |
| 手动 Run workflow（`notify=always`） | 推 | **推**（用于测试/补数据） |
| 未配置 `LIFELOOM_HOOK_URL` | 正常 | 跳过，日志写「未配置…跳过」 |

### 请求体字段说明

顶层：

| 字段 | 含义 | 单位 / 取值 | 缺失时 |
| --- | --- | --- | --- |
| `source` | 上报来源标识，固定 `glados-railgun-checkin` | 字符串 | 不会缺失 |
| `script_version` | 产出这份数据的脚本版本，如 `v1.5.0` | 字符串 | 不会缺失 |
| `reported_at` | 本次上报时间（北京时间，ISO8601 带偏移） | `2026-11-04T17:52:00+08:00` | 不会缺失 |
| `timezone` | 时间字段所用时区，固定 `Asia/Shanghai` | 字符串 | 不会缺失 |
| `trigger` | 本次运行来源：`schedule` 定时 / `manual` 手动触发 / `local` 本机 | 枚举 | 不会缺失 |
| `summary.accounts` | 本轮账号总数 | 个 | 不会缺失 |
| `summary.success` | 本轮签到成功账号数 | 个 | 不会缺失 |
| `summary.already_checked_in` | 本轮「今天已签到」账号数 | 个 | 不会缺失 |
| `summary.failed` | 本轮失败账号数（含 Cookie 失效、鉴权失败） | 个 | 不会缺失 |
| `notification_title` | 同一轮通知的标题原文（一行） | 字符串 | 不会缺失 |
| `notification_text` | 同一轮通知的正文原文（多行，手机端排版好的那份）；请求体超 32KB 时**优先丢弃此字段** | 字符串 | 体积超限时缺失 |
| `accounts` | 账号数组，长度 = 本轮账号数 | 数组 | 不会缺失 |
| `truncated` | 仅当请求体超 32KB 且已截断账号时才出现，恒 `true` | 布尔 | 未截断时缺失 |
| `accounts_omitted` | 仅截断时出现：被省略的账号个数 | 个 | 未截断时缺失 |

`accounts[]` 每个账号：

| 字段 | 含义 | 单位 / 取值 | 缺失时 |
| --- | --- | --- | --- |
| `index` | 该账号在 `COOKIES` 里的顺序号（从 1 开始，跨轮稳定） | 整数 | 不会缺失 |
| `account` | **账号标识**：平台返回的邮箱原文（稳定唯一，可作主键） | 邮箱字符串 | 拿不到邮箱时整字段不给 |
| `account_masked` | 同一账号的脱敏邮箱（`li***d@icloud.com`），仅供展示 | 字符串 | 同上 |
| `platform` | 该账号落在哪个平台：域名以 `railgun` 开头 → `Railgun`，否则 `GLaDOS` | 枚举 | 不会缺失 |
| `domain` | 本轮实际锁定并调用的域名（如 `railgun.info`） | 字符串 | 域名探测就失败时缺失 |
| `checkin_result` | 签到结果：`success` 签到成功 / `already_checked_in` 今天已签过 / `failed` 失败 | 枚举 | 不会缺失 |
| `checkin_code` | 平台返回的原始 code（0 成功、1 已签到、其他为异常） | 整数 | 请求未到达平台时缺失 |
| `checkin_message` | 平台返回的原文消息；失败时即「失败原因原文」，脚本自造的原因（如鉴权失败）也在此 | 字符串 | 无消息时缺失 |
| `checked_at` | 该账号签到动作完成时间（北京时间 ISO8601） | 时间戳 | 未执行到签到步骤时缺失 |
| `earned_points` | **本次**签到获得的积分；`success` 时 `0` 也是真实值，`already_checked_in` 且拿不到数字时不给 | 分 | 见左 |
| `total_points` | 签到后查询到的累计总积分（若发生兑换则为兑换扣减后的余额） | 分 | 积分查询失败时缺失 |
| `remaining_days` | 会员/套餐剩余天数 | 天 | 状态查询失败时缺失 |
| `plan_expires_at` | 套餐到期时间：仅在平台 status 里**确实给出时间值**时上报（时间戳会转成 ISO）；`expired: false` 这类布尔标志不会被误当成日期 | 时间/日期字符串 | 平台未给时间值时缺失 |
| `plan_expires_estimated` | 到期日**推算值**：平台只给「剩余天数」时，用 `system_date + leftDays` 换算成日期，仅供展示（`2026-12-02`） | 日期 `YYYY-MM-DD` | 缺 `leftDays` 或 `system_date` 时缺失 |
| `streak_days` | 连续签到天数：仅当平台 status 明确返回连续签到字段时才给（实测当前接口未提供，故通常不出现） | 天 | 平台未返回时缺失 |
| `attempts` | 该账号本轮实际尝试签到次数（含自动重试，1 = 一次过） | 次 | 不会缺失 |
| `exchange` | 兑换结果对象，仅当本轮**配置了兑换计划**时出现：`status`=`success`/`failed`/`error`/`insufficient_points`/`skipped`，并附 `plan`、`cost_points`、`gained_days`、`remaining_before`、`remaining_after`、`total_points_after`、`message` 等 | 对象 | 本轮未配兑换时缺失 |
| `platform_status` | 平台 status 接口的 `data` **原样透传**（仅剔除 token/cookie/secret/password/session 类键），字段名随平台版本变化，取舍交给你 | 对象 | 状态查询失败、或超 32KB 被瘦身时缺失 |

**两条硬规则**：① 没有的信息**整个字段不给**，绝不填 `0` / `null` / `"-"` 占位；② 宁可多给 —— 平台返回什么就尽量带上，不做多余裁剪。

> 📌 实测（2026-11-04，`railgun.info`）平台 status 返回的字段是：`code, created_at, days, domain, email, expired, hashed, id, leftDays, port, receive_all_emails, refer_id, referral_ratio, site, subscriptions, system_date, system_time, throttle, traffic, vip` —— 全部原样进入 `platform_status`。
> 其中 **`days` 是套餐天数（不是连续签到天数）**，故不会映射成 `streak_days`；`expired` 实测为布尔值，故不会映射成 `plan_expires_at`。日志里会打印本次实际带上的字段清单（只打键名，不打值），方便核对。

### 超过 32KB 怎么瘦身

按「可再生 → 可替代 → 最后才丢账号」的顺序逐级降级，并在日志里写明丢了什么：

1. 丢 `notification_text`（正文与 `accounts` 信息重复）
2. 丢每个账号的 `platform_status`（关键指标已单独提取成字段）
3. 仍然超限才从数组尾部省略账号，并置 `truncated: true` + `accounts_omitted: N`

### 怎么验证 / 排查

手动 **Run workflow** → 「本次是否推送通知」选 `always` → 跑完在 **Run checkin** 日志里找这三行：

```
LifeLoom 上报开始：4 个账号 / 2417 字节
LifeLoom 上报成功：HTTP 201，4 个账号 / 2417 字节，上报时间 2026-11-04T17:52:03+08:00
```

| 日志 | 含义 | 处理 |
| --- | --- | --- |
| `未配置 LIFELOOM_HOOK_URL，跳过 LifeLoom 上报` | Secret 没配或名字拼错 | 补配 Secret |
| `LifeLoom 上报成功：HTTP 201` | 收下了 | 无需处理 |
| `LifeLoom 拒收：HTTP 413 ...` | 请求体超 32KB 且瘦身失败 | 检查账号数是否异常膨胀 |
| `LifeLoom 限流：HTTP 429` | 发太快 | 脚本会自动隔 30 秒重试 |
| `LifeLoom 上报失败：已尝试 3 次后放弃` | 重试 2 次仍失败 | 签到本身不受影响；查 LifeLoom 服务状态 |
| `LifeLoom 上报异常（不影响签到主流程）` | 组装/网络异常 | 同上，签到已完成 |

## ❓ 常见问题

- **签到提示「鉴权失败 / 没有权限」**：Cookie 失效或复制不完整，重新登录获取最新 Cookie 并更新 Secrets。
- **日志中邮箱/Cookie 不完整**：隐私保护自动脱敏。
- **日志时间和收到通知的时间差 8 小时？**：GitHub runner 默认 UTC。v1.1.0 起已强制 `TZ=Asia/Shanghai`，日志为北京时间；旧版日志是同一时刻的 UTC 显示（并非跑错时间）。
- **Actions 被暂停**：内置每月 1 号空提交保活；如仍被暂停，手动触发一次 workflow_dispatch。
- **通知里 `今日已领` 是什么意思**：GLaDOS 每天只能签到得分一次。若当天该账号已签到，接口只返回 `code=1, points=0`（不带当日积分），故显示 `今日已领`。正常情况下每天只会收到一条**带积分**（`今日 +N 积分`）的通知；只有你手动额外触发时才会出现 `今日已领`。
- **一天跑 2 次，会不会收到 2 条通知？**：不会。当天已签到的补跑会**静默跳过推送**；只有「真正签到成功」或「签到失败」才会发通知。
- **签到失败会自动重试吗？**：会。网络错误 / HTTP 错误 / 未知业务失败会隔 5 秒**自动重试一次**（共尝试 2 次）；若是「鉴权失败」（Cookie 失效），重试没有意义，故不重试，通知中会提示重新获取 Cookie。
- **想让每次运行都推送通知（含补跑）？**：在仓库 **Settings → Secrets and variables → Actions → Variables** 加一个变量 `NOTIFY_ALWAYS=true` 即可强制每次都推送。手动触发时也可在 Run workflow 里选 `notify: always`。
- **手动触发和定时触发的通知策略一样吗？**：不一样。手动触发默认**一定推送**（可选 `auto` 改回按策略）；定时触发按策略 —— 只有「真正签到成功」或「签到失败」才推送。
- **Cookie 有有效期吗**：有，会随会话过期，需重新获取。
